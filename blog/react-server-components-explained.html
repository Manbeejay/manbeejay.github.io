React Server Components,
Explained Simply

BJ Chiawa
Designer & Developer
March 5, 2025 8 min read

Last month, I spent a week migrating a medium-sized Next.js app to use React Server Components properly - not just sprinkling in async on a few pages, but actually thinking through the component tree and moving data fetching where it belonged. The app got faster. The code got simpler in some places and more confusing in others. I made some bad decisions early that cost me time later.

This post is what I wished I had before I started. No fluff, no "RSC will change everything" hype - just a clear explanation of what they are, how they differ from what you already know, and when to actually reach for them.

The problem RSC is solving

Before React Server Components, a typical React app had one fundamental shape: JavaScript runs in the browser, components render in the browser, and data comes from an API that your frontend calls. Server-Side Rendering (SSR) muddied this slightly - you could render components on the server for the first HTML payload - but the components themselves were still written as if they'd run on the client. The same bundle, shipped to the browser regardless.

This created a pattern you've almost certainly lived with: fetch data in useEffect, show a loading state, render when the data arrives. For every component that needed remote data, you added a round-trip. Nested components meant nested round-trips. The bundle grew because every library your component imported ended up in the client bundle, even libraries the user never directly interacted with.

The component ran on the server. The bundle still shipped to the browser. RSC breaks that connection.

What React Server Components actually are

A Server Component is a React component that runs only on the server. It never ships to the browser. It can't use useState, useEffect, event handlers, or any browser API - because the browser never runs it. What it can do is read databases directly, call internal APIs without an HTTP round trip, access the filesystem, use server-only secrets, and import large libraries without adding a single byte to the client bundle.

The result of a Server Component is not HTML. It's a serialised description of a UI tree that React knows how to render. This is what makes the mental model different from SSR: the component doesn't run again on the client. It runs once, on the server, and its output flows into the client tree.

The key distinction: SSR renders components on the server to produce HTML, then re-runs the same components on the client to "hydrate" them. Server Components run on the server only. They produce no hydration cost and add no JavaScript to the browser bundle.

Server vs Client Components: the actual rules

In Next.js 13+ with the App Router, every component is a Server Component by default. You opt into client behaviour by adding 'use client' at the top of the file. Here's where most developers get confused at first.

Capability Server Component Client Component
Direct database / filesystem access Yes No
Access server-only secrets Yes No
Async / await at component level Yes No
useState, useEffect, useRef No Yes
Event handlers (onClick, onChange) No Yes
Browser APIs (window, localStorage) No Yes
Adds to JS bundle No Yes
Can render Client Components as children Yes Yes
Can render Server Components as children Yes Only via props (passed from server)

That last row is the subtle one. A Client Component cannot import a Server Component directly, because the client doesn't run Server Component code. But a Server Component can pass another Server Component as a prop to a Client Component - the server resolves both before anything reaches the browser.

What this looks like in practice

Here's a pattern you'll write often. A page fetches data as a Server Component, then passes it down to a Client Component that handles interactivity. 

// app/dashboard/page.tsx — Server Component (no directive needed)
import { db } from '@/lib/db'
import { StatsChart } from './StatsChart'

export default async function DashboardPage() {
  // Runs on the server. db is never exposed to the browser.
  const stats = await db.query('SELECT * FROM monthly_stats')

  return (
    <main>
      <h1>Dashboard</h1>
      {/* Pass the data as a prop to a Client Component */}
      <StatsChart data={stats} />
    </main>
  )
}
// app/dashboard/StatsChart.tsx — Client Component
'use client'

import { useState } from 'react'
import { LineChart } from 'recharts'

export function StatsChart({ data }) {
  const [filter, setFilter] = useState('all')

  // Interactive logic lives here — in the browser
  return (
    <div>
      <select onChange={e => setFilter(e.target.value)}>...</select>
      <LineChart data={data.filter(d => ...)} />
    </div>
  )
}

The database query runs on the server. The chart interaction runs in the browser. The recharts library ships to the client (because StatsChart uses it), but the database driver does not - it only exists in the Server Component, which never reaches the browser.

Mistakes I made, so you don't have to

These are the four things that slowed me down during the migration.

Putting 'use client' too high in the tree

When something breaks because a hook isn't available, the instinct is to add 'use client' to the nearest parent. Resist this. Once a component is a Client Component, every component it imports becomes part of the client bundle too. Push 'use client' down to the smallest component that actually needs browser APIs. A page-level 'use client' usually means you're not getting the benefit of RSC at all.

Trying to pass non-serialisable data as props

Server Components pass data to Client Components across a serialisation boundary. This means props must be serialisable to JSON. Functions, class instances, and Date objects don't pass cleanly. I had a component receiving a Date object from the server and calling .toLocaleDateString() on it in the client — this silently broke. Format dates on the server. Pass strings.

Fetching in the wrong place

I had a habit of fetching at the page level and drilling props down. RSC removes the need for this. Each Server Component can fetch its own data directly - there's no extra HTTP round trip, and Next.js deduplicates identical fetch calls within a request. A UserCard component can fetch the user itself. It doesn't need the page to pass it down. This made my component tree much easier to read once I rewired my thinking.

Forgetting that context doesn't cross the boundary

React context only works in Client Components. If you have a theme, auth, or i18n context that wraps your app, Server Components can't read from it. Pass what they need as props, or access the same source of truth directly on the server (cookies, headers, database).

When to actually use RSC

Not everything benefits from this. Here's a straightforward way to decide.

  • The component fetches data and doesn't need user interaction. Make it a Server Component.
  • The component needs useState, useEffect, or an event handler. Make it a Client Component.
  • The component imports a large library the user never touches (a markdown parser, a syntax highlighter, a PDF renderer). Move it to a Server Component and drop it from the bundle.
  • The component shows different content per request based on cookies or auth. Server Component, using cookies() or headers() from Next.js.
  • You're building a form or anything that needs to respond to user input in real time. Client Component.
A useful heuristic: if the component would be identical for every user who sees it and it needs data from somewhere, it belongs on the server. If it changes based on what the user does after the page loads, it belongs on the client.

What I'd do differently

Start from the leaves, not the root. I began by converting page-level components first, which meant everything below them was broken until I'd worked my way down. Better to start with small, data-only leaf components - product cards, user avatars, article bodies — and move up from there. Each conversion is contained and testable.

Draw the boundary before you write the code. Sketch which components need interactivity and which don't. Mark those as Client Components. Everything else starts as a Server Component and only moves to the client when there's a real reason. This is much easier than converting in the other direction.

The performance gains are real but not automatic. RSC gives you the tools to improve bundle size and eliminate unnecessary round-trips. Whether you actually get those gains depends on where you draw the boundaries. A thoughtless migration gives you the same bundle size you started with, plus a more confusing codebase.

React Server Components are not a replacement for Client Components. They're a new tool with a specific job: running code on the server that has no business running in the browser. If you approach them that way — rather than as a framework rule to comply with - they start making sense quickly.
